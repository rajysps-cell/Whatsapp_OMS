## 2. Voice notes and media not displaying

> "voice notes we don't see. We don't see voice notes. Yes, voice note we need to fix it." — 7:00

**Status: rendering is complete for all six media types — the bug is in retrieval.**

Root cause: media is only fetched when a human opens the thread, and the fetch can only reach
messages still in WhatsApp Web's in-memory collection. **Anything older than the current session
404s permanently.** On top of that, only the image branch has an error fallback — a voice note
whose download fails renders an `<audio>` player that silently does nothing. That is exactly what
"we don't see voice notes" looks like from the outside.

To do:
- Eager-cache media on arrival, using the download path that already works.
- Delete the dead ingest path in `normalize.ts` — it calls the `@lid`-broken `downloadMedia`
  (33/33 failures in the logs, zero files ever written) and the result is discarded anyway.
- Add the image branch's error fallback to audio/video/document.
- `Content-Disposition` on `/api/media` so a PDF saves under its real filename instead of
  `false_1203...@g.us_3EB0....pdf`, and non-PDF documents stop saving as `.bin`.
- One-line fix: `ptv` (round video note) renders when backfilled but not when live.

**Separate question for the client:** voice notes are playable but **not transcribed**, so a
voice-only message has no text and therefore no Extract button. Ask whether that is the real ask.

## 7. Material header lines

> "he put nohub on top, not nohub at the line" — 33:06

A real bug demonstrated live. Some customers write the material once as a header, then list items
under it:

```
Nohub
  2 inch coupling
  3 inch coupling
Sprinkler
  ...
```

Everything under `Nohub` is a nohub item. The app matched a **copper** coupling instead of the
nohub coupling (NHG20 for 2 inch).

Agreed fix in the meeting: a dictionary of static material words (nohub, sprinkler, copper, CXC,
steam…). Dhaval asked for 10–50 words; **Nate agreed to send the list and has not yet.**

**A naive prefix fix will not work.** Measured: prefixing "nohub" onto the line still ranks the
wrong product first (0.557 vs 0.424), and the correct answer scores 0.443 — *below* the 0.45
match threshold. This needs candidate filtering plus a threshold retune when a material is active,
plus a synonym map (the catalog writes "NO HUB" with a space).

Also needed: show which material a line inherited, and let the operator override it — otherwise one
wrong header silently poisons every line beneath it.

**Blocked on Nate for the word list.** A seed list can be derived from the catalog's Major Group
Description values to start.

To do:

cookie does the real work. Confirm that is acceptable.

Also needs an escape hatch for when mail is down — otherwise an SMTP outage locks every user out of
a system that ingests live orders.

## 9. Delete messages

> "I want to be able to delete a message that I sent and it should delete to everyone if I want to"
> — 4:15
> "Delete only for my messages. I don't want anybody to delete a message from somebody else. Every
> user can only delete their own messages." — 6:06

Both options, as in WhatsApp: delete for me / delete for everyone.

**The permission rule is the easy half** — the app already records which OMS user sent each
message, server-side at send time, and that survives the `@lid` chats. The check is one SQL
predicate. It must be enforced on the server; the browser copy may only decide whether to show the
menu item.

**The hard half is reaching the message.** The library's own `Message.delete()` uses the same
lookup this repo already documents as broken on `@lid` chats — the one that forced a custom bypass
for media. Budget real time for this against a live session; it is unknown-unknown work.

Two traps: deleting the local row will not stick (history backfill re-inserts it on the next
reconnect — needs a tombstone), and "delete for everyone" only works inside WhatsApp's own time
window.

**Scope note for the client:** messages typed on the phone, and messages sent before attribution
shipped, have no recorded sender — so under a strict "own messages only" rule nobody in the app can
delete them. Confirm that is intended.

## 11. "Box" quantities

Said in passing, never agreed as work — but this is **not merely missing, it is actively wrong

- `2 box 2 inch coupling` → quantity 2, phrase keeps "box"

pack-size column; only ~43 of 17,393 rows hint at it as free text in the description.

**Needs a client decision on what a box quantity should mean on the order.**
